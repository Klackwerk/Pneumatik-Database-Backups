# Contributing

Issues and pull requests are welcome.

Pneumatik is a backup tool. A bug here loses data that cannot be recreated, so
changes to the dump, storage or retention paths get a closer read than their
size suggests.

## Before you open a pull request

1. Both suites pass:

   ```sh
   cd api && ./gradlew test integrationTest
   cd app && npm run typecheck && npm run lint && npm run build
   ```

2. If you touched `api/src/main/resources/openapi.yaml`, regenerate the typed
   client and commit it:

   ```sh
   cd app && npm run generate:api
   ```

   CI fails when the contract and the generated client drift apart.

3. New API endpoints have contract coverage in
   `api/src/integration-test/groovy/de/klackwerk/pneumatik/api/`.

4. Anything touching backups has a test that would fail without your change.

## Development setup

Requirements: JDK 17+, Node 20+, Docker for the integration databases.

```sh
cd api && ./gradlew bootRun            # → http://localhost:8085, in-memory H2
cd app && npm install && npm run dev   # → http://localhost:5173
```

The generated admin password is printed to the backend log at first start.

`docker-compose.dev.yml` brings up MariaDB and PostgreSQL, both as the
application datastore and as sample databases to back up:

```sh
docker compose -f docker-compose.dev.yml up -d
PNEUMATIK_TEST_DB=mariadb  ./gradlew -p api integrationTest
PNEUMATIK_TEST_DB=postgres ./gradlew -p api integrationTest
```

## House style

* **Backup data never passes through the JVM heap.** Dumps stream to disk,
  uploads stream from it, downloads stream to the client. A change that reads
  an archive into memory will be sent back.
* **Secrets never reach a command line or a log.** Passwords travel through the
  process environment or stdin.

## AI Contributions
* AI Contributions are fine as long as you designed the underlying mechanism yourself 
  and as long as you know what you did and can clearly state what problem you tried
  to solve and what behavior has changed in what way
* All security relevant changes need to be humanly reviewed and explained
* If documentation got generated by AI, it needs to be verified by a human
* Obviously vibecoded, overly verbose low quality code will be denied without further notice

## Changelog

Add a line to the `Unreleased` section of [CHANGELOG.md](CHANGELOG.md) under
Added, Changed, Security or Fixed. One line, stating what changed — the
reasoning belongs in the pull request.

## Security

Do not open a public issue for a vulnerability. See
[SECURITY.md](SECURITY.md).
